# Changelog

All notable changes to Warren are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- The `mac` instance type: a macOS virtual machine per instance on an Apple silicon host, through Lume's API server. New crate `warren-runtime-mac` (clone of a base VM per instance, headless start with a read-only shared folder carrying the gateway and its environment, sleep as suspend with memory kept, host capacity of two macOS guests reported as `409 host_capacity_reached`, copy-on-write backups), new crate `warren-gateway-client` shared with the Firecracker runtime, daemon flags `--runtime none`, `--mac-base-vm`, `--lume-api`, `--lume-bin`, `--mac-vnc`, the built-in template `warren-macos`, `GET /v1/health` reporting `lume`, dashboard/CLI/MCP/SDK support for type `mac`, and the Mac-side scripts `scripts/mac/{build-base.sh,e2e.sh,guest/}`. `docs/macos.md` is the operator guide.
- `warren-gateway`: `GET /v1/stats` (guest-side CPU, memory and disk) and user names from the system user database (Open Directory on macOS, NSS on Linux) when `/etc/passwd` lacks the entry.
- `Runtime::sleep`: runtimes may keep memory across sleep; the lifecycle calls it instead of `stop`. A `host_capacity_reached` refusal on start puts the instance back to `stopped`/`sleeping` instead of `failed`.
- A create request without `type` takes the template's type (`default` when the template allows it, else its first listed type), so `{"template": "warren-macos"}` alone creates a `mac` instance for clients that only know templates. On `mac`, a requested disk below the base image's size is raised to it instead of being recorded as smaller than the VM really is.
- `Runtime::check_capacity`: create and fork ask the runtime whether the host has room before any storage is allocated, so a Mac with two macOS guests running answers `409 host_capacity_reached` at create time instead of cloning a VM it cannot start. Unlimited for the container and Firecracker runtimes.
- Release and install: `.github/workflows/release.yml` builds `warrend`, `warren`, `warren-mcp` and `warren-gateway` for macOS arm64 (ad-hoc signed), Linux x86_64 and Linux arm64 (glibc 2.35 floor, static musl gateway) on tags `v*`, checks the tag against the Cargo workspace version, and publishes tarballs `warren-<version>-<os>-<arch>.tar.gz` with `SHA256SUMS` and notes from this changelog; `scripts/release/{package,checksums,notes,update-formula}.sh` do the work and run locally as a dry run. `scripts/install.sh` is the `curl | sh` installer (OS and CPU detection, SHA-256 verification, `/usr/local/bin` or `~/.local/bin`, no sudo). `packaging/`: a Homebrew formula for the `veerareddyvishal144/homebrew-warren` tap, a systemd unit with an example environment file, a launchd LaunchAgent template, and a docker-compose file for the new root `Dockerfile` (daemon image on `debian:bookworm-slim`, host networking, Docker socket). `docs/install.md` covers every install method, verifying checksums, upgrading, uninstalling and cutting a release.
- The built-in template `warren-claude` and its image `warren/claude` (`images/claude/Dockerfile`, built by `scripts/build-images.sh` after `warren/opencode`): the plain Linux computer with the Claude Code (`claude`), Codex (`codex`) and OpenCode (`opencode`) CLIs installed under `/usr/local`, types `default` and `vm`, no Agent API driver; the CLIs are used over exec or the terminal with provider keys from the instance env. `WARREN_CLAUDE_CODE_VERSION`, `WARREN_CODEX_VERSION` and `WARREN_OPENCODE_VERSION` pin the packages.
- `scripts/mac/build-base.sh --with-agents` (and `install.sh --with-agents` inside the guest): the macOS base image gets Node LTS from the official `darwin-arm64` tarball (newest LTS line in nodejs.org's `index.tab`, or `--node-version`; SHA256 checked against `SHASUMS256.txt`) under `/usr/local`, then `@anthropic-ai/claude-code`, `@openai/codex` and `opencode-ai` installed globally and each checked with `--version` as the guest user. The macOS counterpart of `warren-claude`.
- `warren-runtime-mac`: at startup the runtime lists Lume's VMs and warns about every `warren-<instance id>` VM that has no share directory under `<data-dir>/mac/<id>/`, which this daemon therefore did not create (Lume's local API is unauthenticated); `MacRuntime::foreign_vms` returns the names, the configured base VM excluded.
- `warren up`, `warren down`, `warren status`: the CLI starts the daemon on this machine. `up` finds `warrend` next to `warren` (or on PATH, or `--warrend-bin`/`WARREN_WARREND`), picks the runtime (`--runtime auto|none|docker`; on macOS it requires Lume 0.7.2 and prints the install command when it is missing), refuses a busy port and names the process holding it, installs a launchd LaunchAgent (`dev.warren.daemon`, rendered from `packaging/launchd/dev.warren.daemon.plist` with absolute paths, data under `~/Library/Application Support/Warren`, log under `~/Library/Logs/Warren`) or a systemd user unit (rendered from `packaging/systemd/warrend.service` for user mode, data under `$XDG_DATA_HOME/warren`; when the user cannot talk to Docker it writes the system unit and prints the `sudo` steps instead), or with `--no-service` a detached process with its pid in `<data>/warrend.pid`; then waits for `GET /v1/health`, signs up when the config has no key for that URL, saves the config and prints the dashboard URL, API URL, key location and next steps. `down` stops the service or process (`--purge` also removes the unit or plist and, after confirmation or `--yes`, the data directory); `status` prints the service state, health, runtimes and instance count. What `up` set up is recorded in `daemon.json` next to the CLI config.
- `warren doctor`: one `OK`/`WARN`/`FAIL` line per check with a one-line fix: platform, the `warren`, `warrend` and `warren-mcp` binaries, config and API URL, daemon health and runtimes, who holds the port, the data directory's free space, the service; on macOS Lume's version, `lume serve`, the two-guest limit, the base VM (exists and stopped) and running `warren-*` VMs; on Linux Docker, `runsc` and the `warren/base:<tag>` image. Exit 1 on any `FAIL`.
- `warren mac init [--source VM] [--ipsw latest|PATH] [--target NAME] [--with-agents] [--force] [--dry-run]`: builds the macOS base VM. `scripts/mac/build-base.sh` and `scripts/mac/guest/*` are embedded in the binary and staged in a temporary directory at run time; without `--source` the stock VM is created first with `lume create --os macos --cpu 4 --memory 4GB --disk-size 50GB --ipsw <ipsw> --unattended tahoe` (Lume's offline setup creates the user `lume` with SSH on; on a Lume without `--unattended` the one-time interactive steps are printed and the command waits), a missing `~/.ssh/id_ed25519` is generated, and `--dry-run` prints every step and command without running anything.
- `warren connect <claude|codex|cursor|windsurf|caret|opencode|gemini> [--project] [--print]`: registers `warren-mcp` (found next to `warren`) with the agent, carrying `WARREN_API_URL` and `WARREN_API_KEY` from the config. Claude Code through `claude mcp add --scope user|project` (printed when `claude` is not installed); Codex by merging a `[mcp_servers.warren]` table into `~/.codex/config.toml`; Cursor, Windsurf, Caret and Gemini CLI by merging `mcpServers.warren` into their JSON files; OpenCode by merging `mcp.servers.warren` (`type: local`) into `opencode.json`. Other servers and settings are kept, the previous file is saved as `<file>.bak-<unix time>`, new files are mode 0600, and `--print` shows the result instead of writing. `warren skill install [--project]` writes the Warren skill (`skills/warren/SKILL.md`, embedded) to `~/.claude/skills/warren/SKILL.md` or `.claude/skills/warren/SKILL.md`.
- `docs/quickstart.md` now starts from an installed `warren`: `warren up`, `warren mac init`, `warren connect claude`, the first instance and `warren run -- claude`, for macOS and Linux; `docs/macos.md` and `docs/for-agents.md` point at the same commands.

### Security

- macOS base image: `scripts/mac/build-base.sh` now does what the documentation promised. The guest user's stock password (`lume`) is replaced with a random one (`openssl rand -base64 18`, or `--new-password`), set by `install.sh` with `dscl . -passwd` and verified with `dscl . -authonly`, autologin re-armed with it; the password is stored only on the host at `$WARREN_MAC_DIR/<target>.password` (default `~/.warren/mac`, mode 600) and used for the final in-guest `sudo shutdown`. `install.sh` installs `/etc/ssh/sshd_config.d/100-warren.conf` (`PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PubkeyAuthentication yes`), makes sure `sshd_config` includes the directory and checks the effective configuration with `sshd -T`; the build then confirms from the host that the guest offers `publickey` only. `scripts/mac/debug-guest.sh` reads the password file (or `--password`/`--password-file`) for its `sudo` probes instead of the literal `lume`, and also prints the sshd drop-in, `sshd -T`'s authentication settings and the installed agent CLIs. Existing base images must be rebuilt to get the rotation.

### Changed

- `warren-gateway` now builds on non-Linux hosts (macOS included): the PID 1 code in `init.rs` is compiled only on Linux and other targets get a stub, so `--init` and `POST /v1/shutdown` report `not_supported` there. Groundwork for macOS sandboxes.

- `docs/macos.md`: Phase 0 feasibility results for macOS sandboxes (Lume on Apple silicon) and the Phase 1 design for a `mac` instance type. `scripts/mac/boot-test.sh` measures boot-to-SSH and VM memory.

### Fixed

- macOS guests: the gateway's LaunchDaemon ran it as `lume` in launchd's system domain, where Apple's `nohup` fails ("can't detach from console"), so every background process an agent started through exec died at once. The launcher now runs as root and starts the gateway inside the guest user's own launchd domain (`launchctl asuser` + `sudo -n -E`), where `nohup` works; the base image must be rebuilt with `scripts/mac/build-base.sh`. `scripts/mac/e2e.sh` keeps a `nohup` marker as the regression check and bounds its guest-side `nc` probe with `-G`.
- `warrend` with a relative `--data-dir` (for example `./data-mac`) made every `mac` instance fail at start: the virtiofs share path reached `lume serve` relative to the daemon's directory and Lume refused the run with `ArgumentParser.ValidationError`. The daemon now makes the data directory absolute at startup, and the mac runtime always hands Lume an absolute share path.
- `warren-gateway`'s exec unit test compared a symlinked temp path with the physical one `pwd` prints on macOS.
- `warren-gateway` read its effective uid and gid from `/proc/self/status`, which does not exist on macOS, so `/v1/health` reported `home_owner` as 4294967295 there. It now uses `geteuid`/`getegid` (nix `user` feature).

## [0.1.0] - Unreleased

The first release: a single-node platform in one Rust binary, free software you host yourself.

### Added

- `warrend`: Sandbox API (`/v1`), edge proxy with host-header dispatch, lifecycle and cron in one process; configuration from flags and `WARREN_*` variables; graceful shutdown; reconciler that adopts running containers at startup.
- Workspaces with API keys (`sk_live_...`, SHA-256 at rest) and open signup (`POST /v1/signup` -> `{ "workspace", "api_key", "key_id" }`), switchable with `--signup-enabled`.
- Instances: create, get, list, patch, stop, start, sleep, restart, resize, update, fork, delete; exec with captured output; logs; per-minute metrics; backups and restore; signed URLs.
- Auto-sleep after an idle timeout and wake on request at any instance URL, exec or cron firing; sleeping and stopped instances keep only their disk.
- Awake quota: `--max-awake-instances N` (`WARREN_MAX_AWAKE_INSTANCES`, unset means unlimited) caps the instances a workspace keeps awake at once; enforced on create, start, wake and fork with `409 instance_limit_reached`; `GET /v1/workspace` reports `awake_limit` (number or `null`) and `awake_count`.
- Templates: built-in `warren-base`, `warren-agent` and `warren-opencode`; workspace templates from any image with revisions and `name@rev` pins; in-place updates that keep the persistent disk.
- Edge: workspace-key, signed-URL and cookie authentication on instance hosts, preview URLs for any port, WebSocket passthrough, CORS.
- `warren-gateway` inside every instance: Agent API (`POST /v1/responses` with sessions, SSE streaming, replay and cancel), files API confined to the home directory, exec with a per-instance token, health, `ttyd` supervision on port 7681, PID 1 duties in microVMs; `echo`, `openai` and `command` drivers.
- Runtimes: Docker with gVisor (`runsc`) and a `runc` fallback; experimental Firecracker microVMs (`vm` type) behind `--firecracker`.
- Crons: scheduled prompts for agent instances with five-field schedules and IANA timezones.
- Dashboard: key login, instances, lifecycle actions, terminal via signed URL, exec console, chat, workspace quota.
- Clients: `warren` CLI, MCP server (`warren-mcp`), Rust SDK, one-file Python and TypeScript clients.
- Scripts: `install-gvisor.sh`, `build-images.sh`, `dev-up.sh`, `e2e.sh`, `fetch-firecracker-assets.sh`; Makefile targets for building, testing, images and end-to-end runs.
- Documentation: README, quickstart, concepts, instances, templates, quotas, URLs, Agent API, files, exec, crons, VM instances, self-hosting, for-agents, security, `llms.txt`; CI with fmt, clippy, unit tests, image builds and end-to-end tests; Dependabot for Cargo and GitHub Actions.

### Security

- Tenant network isolation: `warren-net` and `warren-internal` are created with inter-container communication disabled, so instances cannot reach each other over the bridge; Firecracker taps use bridge port isolation. Operators upgrading from an earlier build must remove the old networks once: stop instances, `docker network rm warren-net warren-internal`, restart `warrend`.
- Egress policy: when `warrend` runs as root it installs iptables rules in the `DOCKER-USER` chain (and `FORWARD` rules for the Firecracker bridge) that drop traffic from instances to `169.254.0.0/16` (cloud metadata) always, and to the RFC 1918 ranges and the host's own addresses unless `--allow-private-egress` is set. When not root it logs a warning and installs nothing.
- Gateway authentication: every gateway route except `GET /v1/health` and `/v1/version` requires the per-instance token. The edge and the cron scheduler add it to the requests they forward, so clients never see or send it. The token is no longer inherited by exec shells, agent tool shells or the terminal.
- Edge hardening: a workspace API key sent as `Authorization: Bearer` to an instance URL is no longer forwarded into the instance; CORS on instance hosts allows only the dashboard origin and the instance's own origins; cookie (signed URL) sessions are accepted only for same-origin requests; the signed-URL redirect uses an absolute `Location`; API requests have a 60 s timeout and the listener a global concurrency limit.
- Signup: `--signup-enabled` (default `true`) and a per-IP limit of 10 signups per hour (loopback exempt in `--dev`). Hosted deployments should turn open signup off or put it behind their own flow, and set `--max-awake-instances` so one workspace cannot take the whole host.

### Known limitations

- The base domain should be registered on the Public Suffix List, or each tenant given its own domain, so that instance subdomains are cross-site to each other; browsers otherwise treat `<id>.<base-domain>` hosts as same-site.
- No per-instance egress allowlist; only `allow-all`, `deny-all` and the host-wide block above.
- The awake quota is the only per-workspace limit; CPU, RAM and disk totals per workspace are not enforced, and the bind-mounted home has no filesystem quota.
- The `agent` user has passwordless sudo inside its own instance, and `exec` as `root` is allowed, both by design; there is no privilege boundary inside an instance.
- See [docs/security.md](docs/security.md) for the full list (`runc` fallback, disk quotas, TLS, bearer URLs, side channels, audit log).
